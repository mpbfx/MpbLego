## 排查过程

### 第一阶段：Pod 启动失败 - ES6 模块语法错误

#### 错误日志

```bash
> big-customer@1.0.0 start /app
> cross-env NODE_ENV=production ... node server/index.js

/app/env.js:1
import version from './version'
^^^^^^

SyntaxError: Cannot use import statement outside a module
    at new Script (vm.js:102:7)
    at createScript (vm.js:263:10)
    ...
```

#### 问题分析

1. `env.js` 和 `version.js` 使用了 ES6 的 `import/export` 语法
2. 这两个文件在 Node.js **运行时直接加载**，不经过 Webpack/Babel 编译
3. Node.js 14 在 CommonJS 模式下无法识别 ES6 模块语法

#### 解决方案

**修改 env.js**
```javascript
// 修改前
import version from './version'

// 修改后
const version = require('./version')
```

**修改 version.js**
```javascript
// 修改前
export default version

// 修改后
module.exports = version
```

#### 提交记录
```bash
git add env.js version.js
git commit -m "fix: 修复 ES6 模块语法导致的启动错误"
```

### 第二阶段：node-sass 二进制不匹配

#### 错误日志

```bash
Error: Missing binding /app/node_modules/node-sass/vendor/linux-x64-83/binding.node
Node Sass could not find a binding for your current environment: Linux 64-bit with Node.js 14.x

Found bindings for the following environments:
- Linux 64-bit with Node.js 10.x

This usually happens because your environment has changed since running `npm install`.
Run `npm rebuild node-sass` to download the binding for your current environment.
```

#### 问题分析

1. `node-sass` 包含 C++ 编译的二进制文件，必须在目标环境下编译
2. 本地开发环境可能是 Windows 或 Node 10
3. Docker 运行环境是 Linux + Node 14
4. 原 Dockerfile 先 `COPY . /app`（包括本地 node_modules），导致二进制不匹配

#### 解决方案

**优化 Dockerfile 构建顺序**
```dockerfile
# 修改前
FROM harbor-registry.inner.youdao.com/devops/node:14.17.1-svn
RUN mkdir -p /app
COPY . /app                    # ❌ 复制了本地 node_modules
WORKDIR /app
RUN npm install

# 修改后
FROM harbor-registry.inner.youdao.com/devops/node:14.17.1-svn
RUN mkdir -p /app
WORKDIR /app

COPY package*.json ./          # ✅ 先复制依赖清单
RUN npm install                # ✅ 在 Node 14 + Linux 环境下安装
COPY . .                       # ✅ 再复制代码
```

**创建 .dockerignore**
```
node_modules
npm-debug.log
.git
.gitignore
.vscode
.idea
*.md
!README.md
coverage
.DS_Store
*.log
.env
.env.local
```

#### 提交记录
```bash
git add Dockerfile .dockerignore
git commit -m "fix: 修复 node-sass 二进制版本不匹配问题"
```

### 第四阶段：静态资源 CDN 加载失败

#### 问题分析

查看 `.gitlab-ci.yml` 发现完整的 CI/CD 流程：

```yaml
# 生产环境构建流程
build-online-job:
  stage: build
  script:
    - npm install
    - npm run build              # ✅ 在 CI 阶段构建
    - svn co $CDN_URL            # ✅ 上传静态资源到 CDN
    - cp -r ./nuxt-dist/* ./$prodVersion/
    - svn ci -m "version $prodVersion"
  artifacts:
    paths:
      - '**/*'                   # ✅ 传递构建产物给下一阶段
      - '!**/node_modules/**'

build-image-online-job:
  stage: build-image
  script:
    - docker build -t $IMAGE .  # ✅ 构建镜像（包含 artifacts）
```

**关键发现**：
1. CI 的 build 阶段已经执行 `npm run build`
2. 构建产物通过 `artifacts` 传递给 build-image 阶段
3. 静态资源（JS/CSS）已上传到 CDN
4. Docker 镜像只需要 `COPY . .` 就包含了构建产物

**在 Docker 内重新 build 的问题**：
1. 重新构建生成新的静态资源
2. 但这些资源**没有上传到 CDN**
3. 浏览器尝试从 CDN 加载资源 → 404
4. 触发 `ERR_BLOCKED_BY_ORB`（跨域资源阻止）

#### 正确的解决方案

```dockerfile
# 移除 Docker 内的 build
# RUN npm run build  ← 删除这行

# 只需要复制 CI 阶段的构建产物
COPY . .  # 包含 nuxt-dist/ 目录
```

**更新 .dockerignore**
```diff
node_modules
npm-debug.log
-.nuxt          # ❌ 不要排除构建产物
-nuxt-dist      # ❌ 不要排除构建产物
.git
.gitignore
```

#### 提交记录
```bash
git add Dockerfile .dockerignore
git commit -m "fix: 移除 Docker 内构建，使用 CI 构建产物"
```

### 第五阶段：根本原因 - NODE_ENV 缺失

#### 关键线索

虽然移除了 Docker 内的 build，但问题依然存在。重新审视：
- ✅ dev 环境正常
- ❌ master 环境失败
- 🤔 两个环境的差异在哪里？

#### 深入分析 CI 配置

```yaml
# dev 分支（测试环境）
build-test-job:
  script:
    - npm run build:test  # ✅ 使用 build:test

# master 分支（生产环境）
build-online-job:
  script:
    - npm run build       # ❌ 使用 build
```

#### 检查 package.json

```json
{
  "scripts": {
    // 生产环境（有问题）
    "build": "cross-env NODE_OPTIONS=--max-old-space-size=4096 nuxt build",
    //                  ❌ 缺少 NODE_ENV=production
    
    // 测试环境（正常）
    "build:test": "cross-env NODE_ENV=test NODE_OPTIONS=--max-old-space-size=4096 ... nuxt build",
    //                       ✅ 有 NODE_ENV=test
  }
}
```

#### 影响链分析

**1. env.js 环境判断失效**
```javascript
const createEnv = (NODE_ENV = 'development') => {
  const matchEnv = (NODE_ENV) => {
    switch (NODE_ENV) {
      case 'production':  // ❌ 永远不会匹配（NODE_ENV 是 undefined）
        Object.assign(envMap, baseEnv, onlineEnv)
        break
      case 'test':        // ✅ dev 环境会匹配
        Object.assign(envMap, baseEnv, testEnv)
        break
    }
  }
  return envMap  // ❌ 生产环境返回空对象
}
```

**2. nuxt.config.js 配置错误**
```javascript
module.exports = {
  build: {
    publicPath: projectEnv.BUILD_PUBLIC_PATH,  // ❌ undefined
    // 应该是：https://shared.ydstatic.com/.../online/0.0.6/dist/client/
  },
  env: {
    NODE_ENV: process.env.NODE_ENV,  // ❌ undefined
    WEBSITE_HOST: process.env.NODE_ENV === 'production' 
      ? 'http://f-sales.youdao.com/'  // ❌ 不会执行
      : process.env.WEBSITE_HOST,
  }
}
```

**3. 静态资源路径错误**
- `publicPath` 为 `undefined`
- 浏览器从错误的路径加载 JS/CSS
- 触发 `ERR_BLOCKED_BY_ORB`

#### 最终解决方案

```json
{
  "scripts": {
    "build": "cross-env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=4096 nuxt build",
    //                  ✅ 添加 NODE_ENV=production
    
    "analyze": "cross-env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=4096 nuxt build --analyze"
    //                    ✅ 同时修复 analyze 脚本
  }
}
```

#### 提交记录
```bash
git add package.json
git commit -m "fix: 添加 NODE_ENV=production 到 build 脚本"
git push
```

## 经验教训

### 1. 修改构建脚本要全面测试
- ❌ 只在 dev 环境测试
- ✅ dev 和 master 环境都要测试
- ✅ 关注环境变量的完整性

### 2. 环境变量是关键依赖
- `NODE_ENV` 影响整个构建和运行流程
- 不能因为"看起来不重要"就遗漏
- 要理解每个环境变量的作用

### 3. 理解 CI/CD 流程
- 不要盲目添加构建步骤
- 理解 artifacts 的传递机制
- 理解 Docker 镜像的职责边界

### 4. 代码审查要关注配置文件
- package.json、nuxt.config.js 等配置文件的修改需要特别注意
- 配置文件的改动往往影响范围更广
- 要对比修改前后的完整性

### 5. 排查问题要系统化
- 从错误日志入手
- 理解错误的根本原因，而不是表面现象
- 对比正常环境和异常环境的差异
- 追溯到引入问题的 commit

## 预防措施

### 1. 添加 CI 检查
```yaml
# .gitlab-ci.yml
validate-scripts:
  stage: test
  script:
    - |
      # 检查 build 脚本是否包含 NODE_ENV
      if ! grep -q "NODE_ENV=production" package.json; then
        echo "Error: build script missing NODE_ENV=production"
        exit 1
      fi
```

### 2. 统一构建脚本模式
```json
{
  "scripts": {
    "build": "cross-env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=4096 nuxt build",
    "build:test": "cross-env NODE_ENV=test NODE_OPTIONS=--max-old-space-size=4096 nuxt build",
    "build:dev": "cross-env NODE_ENV=development NODE_OPTIONS=--max-old-space-size=4096 nuxt build"
  }
}
```

### 3. 添加环境变量验证
```javascript
// env.js
const createEnv = (NODE_ENV = 'development') => {
  if (!NODE_ENV) {
    console.warn('⚠️  NODE_ENV is not set, defaulting to development')
  }
  
  const envMap = {}
  // ...
  
  if (Object.keys(envMap).length === 0) {
    throw new Error(`Invalid NODE_ENV: ${NODE_ENV}. Must be 'production', 'test', or 'development'`)
  }
  
  return envMap
}
```

### 4. 文档化部署流程
- 记录完整的 CI/CD 流程
- 说明每个阶段的职责
- 标注关键的环境变量

## 总结

这次生产环境部署失败是一次典型的**配置不完整导致的连锁反应**。虽然表面上看是多个独立的问题（ES6 语法、node-sass、构建产物、静态资源），但根本原因只有一个：**commit b5cdf41 修改 build 脚本时遗漏了 `NODE_ENV=production`**。

排查过程中的关键转折点是**对比 dev 和 master 环境的差异**，这让我们找到了真正的根本原因。

**核心教训**：修改构建配置时，要确保所有环境的脚本保持一致性和完整性，不能因为"看起来不重要"就遗漏关键的环境变量。
