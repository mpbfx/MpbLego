# 技术挑战总览：端到端故事线（big-customer，面向面试）

> 目标：把项目里最有技术挑战的点串成一条“从用户请求到发布上线”的端到端叙事，面试时可以按这条线讲清楚架构、关键取舍与落地细节，并指到代码。

## 1. 一句话概括（面试开场）

这是一个 Nuxt 2 SSR 系统，在同一套工程内承载“大客户系统 + /translator 子站”，通过 Nuxt plugin 统一 HTTP/鉴权与状态同构，通过 webpack/nuxt extend 解决 SSR 兼容与大依赖分包，通过 CI/CD 把构建产物版本化发布到 SVN/CDN，并用 Harbor 镜像 + K8S（ydci）实现可追溯部署与回滚。

## 2. 端到端主链路（从浏览器到上线）

### Step A：用户访问页面（SSR 首屏渲染）

- SSR server 入口是 Express 承载 Nuxt：`server/index.js:1`
- `nuxt.config.js` 决定监听地址与端口：`nuxt.config.js:41`

关键代码摘录（SSR server）：

```js
// server/index.js
const config = require('../nuxt.config.js')
config.dev = process.env.NODE_ENV !== 'production'
const nuxt = new Nuxt(config)
if (config.dev) await new Builder(nuxt).build()
else await nuxt.ready()
app.use(nuxt.render)
app.listen(port, host)
```

面试要点：

- SSR 冷启动/重启成本高，所以生产通常不 runtime build（详见 `docs/面试问答/运行部署-PM2-Docker-详解.md:1`）。

### Step B：服务端初始化登录态（nuxtServerInit）

- 核心入口：`store/index.js:14`
- 关键挑战：SSR 端需要基于 cookie 判断登录态，并把用户信息灌入 Vuex，避免首屏闪烁。

关键代码摘录（按访问路径分流）：

```js
// store/index.js
const isTranslatorPage = (req.url || '').startsWith('/translator')
if (isTranslatorPage) {
  const validUserRes = await app.$http.get(path.isValidUser)
  store.commit('userinfo/UPDATE_USERINFO', { userName: username, roleName: role, isValid: valid })
  store.commit('SET_AUTH_USER', true)
} else {
  const userinfoRes = await app.$http.get(path.getUserInfo)
  store.commit('userinfo/UPDATE_USERINFO', userinfoRes.data)
  store.commit('SET_AUTH_USER', true)
}
```

面试要点：

- “同一 Nuxt 工程的双子站”在 SSR 初始化阶段就分流（translator vs 大客户系统）。

### Step C：页面发起请求（HTTP 封装 + 错误码策略）

- 核心封装：`plugins/http.js:5`（注入 `$http`）
- 关键挑战：SSR/CSR cookie 透传、统一错误码跳转、不同 Content-Type 提交策略。

关键代码摘录（1003 未登录跳转 + post 策略）：

```js
// plugins/http.js
instance.onResponse(resp => {
  if (resp.data.errorCode === 1003) redirect(`${path.loginUrl}=${process.env.WEBSITE_HOST}${route.fullPath}`)
  return resp.data
})

post: (url, data, type) => {
  if (type === 'query') return instance({ data: qs.stringify(data), headers: { post: { 'Content-Type': 'application/x-www-form-urlencoded' } } })
  if (type === 'formData') return instance({ data, headers: { 'Content-Type': 'multipart/form-data' } })
  return instance({ data })
}
```

面试要点：

- 同项目存在 `$http` 与 `$api` 两套封装（`plugins/axios.js:3`），是典型工程债/一致性挑战（见 `docs/面试问答/项目难点-补充.md:1`）。

### Step D：权限与可编辑性（role 权限 + 字段级权限 + 状态机）

这一段是项目“业务复杂度最高”的地方：不仅要控制按钮显示，还要控制“字段在不同阶段能否编辑/必填”。

- UI 级权限（指令策略）：`plugins/checkPermission.js:9` + `config/permission.js:1`
- 字段级权限矩阵：`config/resourceFieldPermission.js:61`
- 状态机映射：`config/resourceStatus.js:5`

关键代码摘录（字段权限矩阵）：

```js
// config/resourceFieldPermission.js
export const fieldPermissions = {
  contract: {
    signDate: { development: { editable: true }, onsite: { editable: true, required: true } }
  }
}
```

面试要点：

- role 权限更偏“功能可见性”，字段权限更偏“业务状态机驱动的数据可编辑性”，两者要协同。

### Step H：CI/CD 发布（SVN/CDN -> Docker -> Harbor -> K8S）

发布链路由 `.gitlab-ci.yml` 编排：

- `build`：`nuxt build` 产物在 `nuxt-dist/`（`nuxt.config.js:45`），并上传到 SVN/CDN 版本目录（`.gitlab-ci.yml:40`）。
- `build-image`：`docker build` 把产物带进镜像，push 到 Harbor（`.gitlab-ci.yml:60`）。
- `deploy`：`ydci deploy set-image ...` 切 K8S workload 镜像到 `CI_COMMIT_SHA`（`.gitlab-ci.yml:73`）。

面试要点：

- 版本化 CDN + 镜像 tag = 可追溯、可回滚（定位到具体 commit）。

## 3. 面试用“总结话术”（30 秒版本）

我会把项目分成四层讲：

1) **运行层**：Express + Nuxt SSR，生产不 runtime build；  
2) **数据层**：Nuxt plugin 注入 `$http`，错误码集中处理，SSR 透传 cookie；  
3) **规则层**：role 权限、字段级权限矩阵、资源状态机驱动的可编辑性；  
4) **交付层**：CI build -> SVN/CDN 版本化 -> 镜像 -> Harbor -> K8S 切镜像，配合分包/分析脚本持续优化性能。

## 4. 进一步可讲的“技术挑战亮点”（可选）

- 双子站（translator）在同一 Nuxt 中的隔离与复用：layout 挡板 + 业务模块工厂组合；
- 文件上传/下载/预览：多类型、跨模块复用、credentials、blob 预览；
- 性能度量脚本：用 manifest 与 build log 给出“可对比指标”，让优化可审计。
