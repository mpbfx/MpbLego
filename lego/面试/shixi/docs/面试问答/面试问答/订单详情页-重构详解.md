# 订单详情页-重构详解（big-customer，面向面试）

> 目标：把订单详情页从“超大单页（monolith）”重构为“卡片化 + 局部刷新 + SSR 首屏减负”的过程，讲成能落到代码的面试答案（含旧版对照与关键代码索引）。

## 1. 一句话概括（面试开场）

订单详情页重构的本质是一次“**结构重构 + 数据获取策略重构**”：

- 旧版：`pages/orderManagement/orderDetail.vue.backup:1` 把“基础信息表单/生产记录/收益/操作记录/评价弹窗/API/权限”堆在一个页面里，SSR `asyncData` 全量并发拉取，改动成本和首屏阻塞都很高。
- 新版：`pages/orderManagement/orderDetail.vue:1` 把页面拆成“页面编排层 + 业务卡片层”，SSR 只拿基础信息（可渲染首屏），其余卡片在 `mounted` 后并发懒加载；所有写操作后只做相关卡片的局部刷新。

---

## 2. 页面入口与业务场景（你可以这样讲）

订单详情页的两个核心场景：

### A) 新建订单（无 `query.id`）

- SSR 预填（PM 最近一单作为模板）+ 进入客户信息卡编辑态：`pages/orderManagement/orderDetail.vue:261`、`pages/orderManagement/orderDetail.vue:363`
- 保存成功后不跳页：`router.replace` 注入新 id，并刷新二级卡片：`pages/orderManagement/orderDetail.vue:483`、`pages/orderManagement/orderDetail.vue:1136`

### B) 编辑订单（有 `query.id`）

- SSR 只拿基础信息（可渲染客户信息卡），二级卡片数据（生产/收益/操作记录）在 mounted 后并发加载：`pages/orderManagement/orderDetail.vue:261`、`pages/orderManagement/orderDetail.vue:374`

面试讲法：

- 这是一条典型的“先首屏可见 → 再补齐信息”的体验链路：新建能快速进入编辑；编辑能快速看到订单基础信息，附属信息异步补齐。

## 3. 结构重构：从“单页大表单”到“卡片化编排”

旧版的典型特征是：页面 template 直接堆 Ant Design Vue 的 `a-form + v-decorator`，字段/校验/联动散落在 template 和 methods 里，典型片段：

- `a-form`：`pages/orderManagement/orderDetail.vue.backup:10`
- `v-decorator` + `disableEditBasicInfo`：`pages/orderManagement/orderDetail.vue.backup:21`

新版把一个订单拆成 4 张卡片，页面只负责“编排 + 数据流”：

- 客户信息：`components/OrderDetail/Cards/CustomerInfoCard.vue:1`（挂在 `pages/orderManagement/orderDetail.vue:14`）
- 生产信息：`components/OrderDetail/Cards/ProductionInfoCard.vue:1`（挂在 `pages/orderManagement/orderDetail.vue:35`）
- 收益信息：`components/OrderDetail/Cards/ProfitInfoCard.vue:1`（挂在 `pages/orderManagement/orderDetail.vue:54`）
- 操作记录：`components/OrderDetail/Cards/OperationRecordCard.vue:1`（挂在 `pages/orderManagement/orderDetail.vue:74`）

对应代码摘录：

```vue
<!-- pages/orderManagement/orderDetail.vue:11 -->
<div class="cards-container">
  <div class="card-section">
    <customer-info-card :order-info="orderInfo" @save="saveCustomerInfo" />
  </div>

  <div v-if="orderId && !isSalesRole" class="card-section">
    <production-info-card :records="orderTranslateRecordList" @save-row="saveProductionRow" />
  </div>

  <div v-if="orderId" class="card-section">
    <profit-info-card :profit-data="orderProfitList" />
  </div>

  <div v-if="orderId && !isSalesRole" class="card-section">
    <operation-record-card :records="orderOperationRecordList" />
  </div>
</div>
```

面试讲法：

- 页面拆分的标准不是“UI 组件”，而是“业务域”：客户/生产/收益/审计。拆分后每张卡可独立迭代/独立 loading/独立刷新，降低回归范围。

## 4. 数据获取策略重构：asyncData 从“全量 SSR”到“首屏减负 + mounted 懒加载”

### A) 旧版：SSR asyncData 全量并发拉取

旧版在有 id 时 `asyncData` 会一次性 `Promise.all` 拉取订单 + 用户 + 操作记录 + 生产记录 + 收益（并且还在 map 里拼装行配置）：

来源：`pages/orderManagement/orderDetail.vue.backup:1538`

```js
let [
  sellerNameListRes,
  orderListRes,
  orderInfoRes,
  orderOperationRecordListRes,
  orderTranslateRecordListRes,
  salesOrderProfitRes,
] = await Promise.all([
  app.$http.get(path.getSalesManagerNameList),
  app.$http.get(path.getSalesOrderById, playload),
  app.$http.get(path.getSalesUserByOrderId, playload, 'query'),
  app.$http.get(path.getOrderOperationRecordList, playload),
  app.$http.get(path.getOrderTranslateRecordList, playload),
  app.$http.get(path.getSalesOrderProfit, playload, 'query'),
])
```

问题（面试里可以点出来）：

- 首屏必须等“生产/操作记录/收益”都返回才能渲染，慢接口会拖累 TTFB/首屏体验。
- 页面一处功能改动容易牵扯全量回归（因为所有逻辑都在一个 `.vue` 内）。

### B) 新版：SSR 只拿“基础信息”，二级卡片延后并发加载

新版在有 id 时 `asyncData` 只拉：卖方列表 + 订单基础信息 + 用户名（客户名），其余卡片数据不在 SSR 阶段取：

- `asyncData`：`pages/orderManagement/orderDetail.vue:261`、`pages/orderManagement/orderDetail.vue:323`
- `mounted` 触发：`pages/orderManagement/orderDetail.vue:363`
- 二级卡片并发：`pages/orderManagement/orderDetail.vue:374`、`pages/orderManagement/orderDetail.vue:380`

对应代码摘录：

```js
// pages/orderManagement/orderDetail.vue:374
async loadSecondaryCards() {
  if (!this.orderId) return
  const tasks = [this.refreshProfitInfo()]
  if (!this.isSalesRole) tasks.push(this.refreshProductionInfo(), this.refreshOperationRecord())
  await Promise.all(tasks)
}
```

面试讲法：

- 这不是“少请求”，而是“把请求放到正确的阶段”：首屏只取“必要渲染数据”，让页面先可用，再并发补齐二级信息。
- 每张卡都有独立 loading（`customerLoading/productionLoading/profitLoading/operationLoading`），用户能感知到“正在加载”，而不是整页空白。

## 5. 数据流重构：从“updatePage 全量刷新”到“按卡片局部刷新”

### A) 旧版：updatePage + initDatetime/initOrderInfo 驱动全量更新

旧版大量写操作后会 `updatePage()`，再 `initDatetime()` / `initOrderInfo()`，带来：滚动位置、局部编辑态、临时状态更容易被重置。

- `mounted`：`pages/orderManagement/orderDetail.vue.backup:1424`
- `updatePage`：`pages/orderManagement/orderDetail.vue.backup:1811`

### B) 新版：refresh* 只刷新“受影响卡片”

新版把刷新拆成：

- `refreshCustomerInfo`：仅刷新订单基础信息与客户名：`pages/orderManagement/orderDetail.vue:501`
- `refreshProductionInfo`：仅刷新生产记录列表：`pages/orderManagement/orderDetail.vue:854`
- `refreshProfitInfo`：仅刷新收益：`pages/orderManagement/orderDetail.vue:883`
- `refreshOperationRecord`：仅刷新操作记录：`pages/orderManagement/orderDetail.vue:1050`

面试讲法：

- “按域刷新”能让写操作后的 UI 更稳定：不影响其他卡片的滚动/折叠/编辑态；也减少接口与 DOM 的无谓消耗。

## 6. 关键业务：客户信息保存（基础字段 + 结算节点一致性）

客户信息保存不是简单的 `updateSalesOrder`，因为它还包含“结算节点链路”（交付/提单/确认/回款）的一致性维护。

新版做法：一次点击保存里，把基础字段和结算节点拆开处理：

1) 先提交基础字段：`updateSalesOrder`
2) 对结算节点做 diff（旧值 vs 新值）
3) 按链路“**先取消（回滚）→ 再确认（推进）**”，逐个调用后端接口，避免出现非法状态

来源：`pages/orderManagement/orderDetail.vue:387`

```js
// pages/orderManagement/orderDetail.vue:390
const settlementKeys = ['translateFinishTime', 'sendBillTime', 'incomeFinishTime', 'rebateFinishTime']

// 先取消（回滚链路：回款 -> 确认 -> 提单 -> 交付）
for (const key of [...settlementKeys].reverse()) {
  if (prevSettlement[key] && nextSettlement[key] !== prevSettlement[key]) {
    await this.$http.post(cancelApiMap[key], { id: this.orderId }, 'query')
  }
}

// 再确认（推进链路：交付 -> 提单 -> 确认 -> 回款）
for (const key of settlementKeys) {
  if (nextSettlement[key] && nextSettlement[key] !== prevSettlement[key]) {
    await this.$http.post(saveApiMap[key], { id: this.orderId, confirmDate: nextSettlement[key] }, 'query')
  }
}
```

面试讲法：

- 这是一种“把业务状态机显式化”的写法：前端用顺序控制保护链路一致性，避免用户在 UI 上把“后置节点”改到“前置节点”之前。

## 7. 关键业务：生产信息（新增/编辑/日期确认）与收益联动

生产信息的重构点主要是“操作闭环更清晰，刷新范围更小”：

- 新增/编辑生产记录成功后：只刷新生产/收益/操作记录，并把卡片切回 view：`pages/orderManagement/orderDetail.vue:820`
- 生产记录数值校验：总价/字数仅支持两位小数：`pages/orderManagement/orderDetail.vue:651`
- 单独编辑日期走专用确认接口（交付/结算），保存成功只刷新生产信息：`pages/orderManagement/orderDetail.vue:901`
- 低毛利提示作为“软提醒”：保存生产信息后触发校验：`pages/orderManagement/orderDetail.vue:746`

面试讲法：

- 把“生产记录编辑”和“结算节点链路”分开：生产记录日期走专用接口，既贴合后端契约，也能把刷新范围压到最小。

## 8. 评价弹窗：为什么保留在页面层（而不是塞进卡片里）

评价弹窗是“跨卡片”的临时编辑 UI（从生产记录点出），保留在页面层能：

- 避免卡片之间互相依赖（生产卡不需要 import modal）
- 保存成功后统一刷新操作记录（审计链路）：`pages/orderManagement/orderDetail.vue:1126`

入口与保存：

- 打开弹窗：`pages/orderManagement/orderDetail.vue:1064`
- 保存评价：`pages/orderManagement/orderDetail.vue:1088`

## 10. 常见坑 & 可改进点（面试加分）

1) `loadSecondaryCards` 与 `refreshPage` 的职责边界：目前新建订单成功后走 `refreshPage()` 全量拉取，后续可改成只调 `loadSecondaryCards()` + `refreshCustomerInfo()`，进一步减少接口量（`pages/orderManagement/orderDetail.vue:1136`）。
2) 结算节点链路目前在页面层维护：如果未来拆出 `CustomerSettlementCard`（已保留入口），建议把“链路状态机 + 接口映射”抽成纯函数并加单测（入口注释：`pages/orderManagement/orderDetail.vue:60`）。
3) 旧版 `.backup` 仍在仓库：如果是长期保留用于回滚，对应文档应明确；否则建议迁移到 git tag 或归档目录，避免被误引用（`pages/orderManagement/orderDetail.vue.backup:1`）。
4) SSR 首屏减负已完成，但如果要进一步优化感知速度，可考虑：二级卡片骨架屏、IntersectionObserver 进入视口再加载（配合 `docs/订单详情页性能优化-asyncData拆分与卡片懒加载.md:1`）。
