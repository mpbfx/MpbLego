# 生产环境排障实战复盘详解（big-customer，面向面试）

> 目标：把一次真实的"生产部署失败 → 5 阶段排查 → 根因定位 → 修复 → 防御"全过程整理成面试可讲的故事线，展示系统排查能力和工程成熟度。

## 1. 一句话概括（面试开场）

一次 master 分支部署后 **K8s Pod 反复重启**，表面看是 5 个独立问题（ES6 语法 / node-sass 二进制 / 缺构建产物 / CDN 404 / 白屏），但根因只有一个：**修改 `package.json` 的 `build` 脚本时遗漏了 `NODE_ENV=production`**，导致所有环境变量和 CDN 路径配置失效，最终导致级联故障。

生产环境 Pod 反复重启，**生产服务不可用**，需要快速定位并恢复。

## 3. 排查过程详解（面试重点讲 2-3 轮即可）

### 第 1 阶段：Pod 启动报 ES6 语法错误

**现象**：

```
SyntaxError: Cannot use import statement outside a module
  at /app/env.js:1
```

**分析**：`env.js` 和 `version.js` 使用了 `import/export`（ES6 模块语法），但这两个文件在 Node.js 运行时**直接加载**，不经过 Webpack/Babel 编译。Node 14 的 CommonJS 模式无法识别 ES6 模块语法。

**修复**：

```js
// env.js: import → require
const version = require('./version')
// version.js: export default → module.exports
module.exports = version
```

**面试讲法**：这说明我理解 Nuxt SSR 中"哪些文件走 Webpack 编译、哪些文件由 Node 直接加载"的边界。`server/index.js` → `nuxt.config.js` → `env.js` → `version.js` 这条链全部是 Node 直接 require，不经过 Babel。

---

### 第 2 阶段：node-sass 二进制不匹配

**现象**：

```
Missing binding: Linux 64-bit with Node.js 14.x
Found bindings for: Linux 64-bit with Node.js 10.x
```

**分析**：`node-sass` 包含 C++ 编译的二进制文件。原 Dockerfile 先 `COPY . /app`（包括本地 node_modules），再 `npm install`，导致本地编译的二进制不适用于 Docker 环境。

**修复**：优化 Dockerfile 构建顺序 + 添加 `.dockerignore`。

```dockerfile
# 修改前（错误）
COPY . /app
RUN npm install

# 修改后（正确）
COPY package*.json ./
RUN npm install
COPY . .
```

**面试讲法**：Dockerfile 的**层缓存优化**——先拷贝 `package*.json` 并安装依赖（只有 package lock 变了才重新安装），再拷贝源码。同时 `.dockerignore` 排除 `node_modules`，确保在目标环境重新编译原生依赖。

---

### 第 3 阶段：缺少构建产物（误判）

**现象**：

```
Renderer resources are not loaded!
Please check dist (/app/nuxt-dist/dist/server) exists.
```

**误操作**：在 Dockerfile 中添加了 `RUN npm run build`。

**导致新问题**：浏览器大量 `ERR_BLOCKED_BY_ORB` 错误，页面完全白屏无样式。

**面试讲法**：这是我犯的**误判**——没有理解完整的 CI/CD 流程就盲目改 Dockerfile。真正的了解后发现：

- CI `build` 阶段已经构建并上传 CDN。
- `artifacts` 机制把构建产物传递给 `build-image` 阶段。
- Docker 镜像中已有构建产物，不需要再构建。
- 在 Docker 内重构建 → 生成新哈希 → CDN 上没有这些新文件 → 404。

**教训**：排查问题时要先理解完整链路，不要"看到什么修什么"。

---

### 第 4 阶段：静态资源从错误路径加载

**现象**：移除 Docker 内 build 后，仍然白屏。浏览器控制台显示 JS/CSS 从错误路径加载 → 404。

**分析**：检查构建产物发现 `publicPath` 为 `undefined`——静态资源地址就是空的。

追溯到 `env.js`：

```js
const matchEnv = NODE_ENV => {
  switch (NODE_ENV) {
    case 'production': // ← 如果 NODE_ENV 不是 'production'，不匹配
      Object.assign(envMap, onlineEnv)
      break
  }
}
return envMap // ← 空对象！
```

---

### 第 5 阶段（根因）：NODE_ENV 缺失

**关键线索**：dev 环境正常、master 环境失败 → 对比两个环境的 npm scripts：

```json
// 测试环境（正常）
"build:test": "cross-env NODE_ENV=test ... nuxt build"
//                       ✅ 有 NODE_ENV

// 生产环境（异常）
"build": "cross-env NODE_OPTIONS=--max-old-space-size=4096 nuxt build"
//                  ❌ 缺少 NODE_ENV=production
```

**因果链**：

```
NODE_ENV 缺失
  → env.js 返回空对象
    → BUILD_PUBLIC_PATH = undefined
      → nuxt.config.js: publicPath = undefined
        → 静态资源路径错误
          → 浏览器 404 / ERR_BLOCKED_BY_ORB
            → 页面白屏 + K8s 健康检查失败
              → Pod 反复重启
```

**修复（1 行）**：

```json
"build": "cross-env NODE_ENV=production NODE_OPTIONS=--max-old-space-size=4096 nuxt build"
```

## 5. 防御措施（面试加分项）

### A) CI 检查脚本

```yaml
validate-scripts:
  script:
    - |
      if ! grep -q "NODE_ENV=production" package.json; then
        echo "Error: build script missing NODE_ENV=production"
        exit 1
      fi
```

### B) env.js 增加防御

```js
const createEnv = (NODE_ENV = 'development') => {
  if (!NODE_ENV) {
    console.warn('⚠️ NODE_ENV is not set')
  }
  // ...
  if (Object.keys(envMap).length === 0) {
    throw new Error(`Invalid NODE_ENV: ${NODE_ENV}`)
  }
}
```

### C) 统一脚本模式

```json
{
  "build": "cross-env NODE_ENV=production ... nuxt build",
  "build:test": "cross-env NODE_ENV=test ... nuxt build",
  "build:dev": "cross-env NODE_ENV=development ... nuxt build"
}
```

## 6. 面试题库（Q&A 速记）

### Q1：你遇到过最复杂的线上问题是什么？

master 分支部署后 K8s Pod 反复重启。表面是 5 个问题叠加，但根因只有一个：`package.json` 的 build 脚本遗漏了 `NODE_ENV=production`，导致 CDN 路径配置全部失效，静态资源 404，页面白屏。

### Q2：你是怎么排查的？

关键转折是**对比 dev 和 master 环境的差异**。dev 环境正常说明代码本身没问题，问题出在 master 特有的配置/构建流程上。最终通过对比两个分支的 npm scripts 发现 `NODE_ENV` 缺失。

### Q3：你从这次事故学到了什么？

三点：1) **修改构建配置必须全面测试**——不能只测 dev 不测 prod；2) **要先理解完整 CI/CD 流程再排查**——第 3 阶段我就是因为不了解链路做了错误修改；3) **关键配置要有防御校验**——env.js 应该在配置为空时 throw Error 而不是静默返回空对象。

### Q4：NODE_ENV 为什么这么重要？

在本项目中 `NODE_ENV` 是构建链的根依赖：决定了 CDN 路径（publicPath）、API 地址（API_HOST）、运行时行为（dev/prod 模式）。缺失它 = 全链路配置失效 = 级联故障。

### Q5：你怎么防止类似问题再次发生？

三层防御：1) CI 检查脚本自动验证 build 脚本包含 `NODE_ENV`；2) `env.js` 增加空值校验和 throw；3) Code Review 时对 `package.json` 等配置文件的修改加强审核。

### Q6：这次排查中你做错了什么？

第 3 阶段我在不了解 CI 流程的情况下，在 Dockerfile 中加了 `npm run build`，导致新构建产物的哈希和 CDN 上的不一致，反而让问题更严重。这说明**排查前要先理解系统全貌**。

## 7. 面试讲法建议

### 30 秒速答

生产部署后 Pod 反复重启，根因是修改构建脚本时遗漏了 `NODE_ENV=production`，导致 CDN 路径失效、页面白屏。通过对比正常环境和异常环境的差异定位到根因，1 行修复后增加了 CI 校验和配置防御。

### 2 分钟展开

按"现象 → 误判 → 转折 → 根因 → 修复 → 防御"讲：

1. 现象：K8s Pod 反复重启，dev 正常 master 挂。
2. 误判：以为是 Docker 内缺少构建产物，在 Dockerfile 加了 build。
3. 转折：加了 build 反而更严重（CDN 哈希不一致），说明不该在 Docker 内构建。
4. 根因：对比 npm scripts 发现 `build` 缺少 `NODE_ENV=production` → env.js 返回空 → publicPath undefined → 静态资源 404。
5. 修复：`package.json` 加 `NODE_ENV=production`。
6. 防御：CI 校验 + env.js 空值 throw + Code Review 门禁。

### 3 分钟深讲（带因果链）

在 2 分钟版基础上加：

- `NODE_ENV → env.js → nuxt.config.js → publicPath → 浏览器 → 404 → Pod` 完整因果链。
- 不同阶段我的思考过程和判断依据。
- 从这次事故提炼的方法论：**对比法**（正常 vs 异常）、**追溯法**（从表象追到配置根源）、**全链路理解**（不理解就容易误判）。
