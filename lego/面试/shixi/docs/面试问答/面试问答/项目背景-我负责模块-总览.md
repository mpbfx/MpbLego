# 项目背景 & 我负责模块总览（big-customer，面向面试）

> 目标：把“这是个什么系统、你在里面负责了什么、关键页面怎么设计、为什么这么做”讲清楚，并能直接指到代码。

## 1. 项目一句话（面试开场）

这是一个 **人工翻译大客户订单管理系统（Nuxt 2 SSR）**，面向内部（销售/PM/运营）完成订单全流程管理，同时给译员提供“自助维护资料/查看合同/薪资”的轻量入口（`nuxt.config.js:28`、`pages/translator/index.vue:1`）。

我主要负责的业务面：**资源（译员/供应商）全链路** + **订单管理核心链路** + **译员平台**。

## 3. 资源开发列表（开发池）：为什么是“筛选 + 表格 + 快捷动作”

### 业务定位

开发池解决的问题是：**高频筛选、快速对比、快速进入详情补齐信息、关键节点入库**。

### 核心设计点（可以直接讲“我怎么做的”）

1) **筛选组件抽离**：列表页把筛选条件复杂度收敛到 `ResourceFilter`，主页面只关心“接收筛选事件 → 请求数据 → 渲染表格”（`pages/resourceManagement/interpreterAndSuppliers.vue:5`）。
2) **自定义列（用户可配置）**：用 `CustomColumnDropdown` + localStorage key 做“列显隐持久化”，减少“列太多看不清”的问题（`pages/resourceManagement/interpreterAndSuppliers.vue:25`）。
3) **表格单元格可读性优化**：对长字段用 tooltip + 截断展示，保证横向滚动可用（`pages/resourceManagement/interpreterAndSuppliers.vue:41`）。
4) **快捷动作**：沟通/简历/删除/入库都在 action 栏聚合（`pages/resourceManagement/interpreterAndSuppliers.vue:106`～`pages/resourceManagement/interpreterAndSuppliers.vue:114`）。
5) **状态机接入（行内编辑状态）**：列表页复用状态机配置，控制“是否可编辑、可流转到哪些状态”（`pages/resourceManagement/interpreterAndSuppliers.vue:504`、`pages/resourceManagement/interpreterAndSuppliers.vue:1787`）。

### 关键数据请求入口

列表默认拉取使用：`getDevelopResourcePage`（`config/path.js:25`），在页面内集中在 `getSalesTranslatorPage`：

```js
// pages/resourceManagement/interpreterAndSuppliers.vue:1486
const res = await this.$http.get(path.getSalesTranslatorPage, {
  pageIndex: this.translatorListCurrentPageIndex,
  pageSize: 50,
})
```

### 典型“我做的难点”例子：列表页直接跳简历预览

为了减少点进详情再找简历的成本，列表里 `goToDetailSection(..., 'resume')` 会先查最新简历，再跳预览页（`pages/resourceManagement/interpreterAndSuppliers.vue:1712`）。

```js
// pages/resourceManagement/interpreterAndSuppliers.vue:1720
const resumeRes = await this.$http.get(path.getResourceResumeByResourceIdAndType, { resourceId: id, fileType: 1 })
// pages/resourceManagement/interpreterAndSuppliers.vue:1736
const fileUrl = `${path.baseURL}${path.downloadFile}?keyName=${resumeFile.keyName}&fileName=${encodedFileName}`
// pages/resourceManagement/interpreterAndSuppliers.vue:1739
this.$router.push({ path: `/resourceManagement/resumePreview/${id}`, query: { url: fileUrl, from: 'development' } })
```

## 4. 资源在场列表（已入库池）：和开发池“同 UI，不同规则”

### 业务定位

在场池解决的问题是：**资源已经可用**，更多是“查、筛、对比、看历史能力/价格/接单情况”，对“删除/强修改”会更谨慎。

### 关键差异点（讲得出“为什么不同”）

- 筛选组件换成 `OnSiteFilter`（字段与开发池不完全一样）：`pages/resourceManagement/onSite.vue:5`
- 列配置存储 key 独立，避免互相污染：`pages/resourceManagement/onSite.vue:21`
- 数据接口换成 stored 系列：  
  - 默认列表：`getStoredResourcePage`（`config/path.js:28`、`pages/resourceManagement/onSite.vue:700`）  
  - 条件筛选：`searchStoredResourceListByCondition`（`config/path.js:29`、`pages/resourceManagement/onSite.vue:662`）

## 5. 资源详情页（核心）：卡片化 + 状态机/字段权限 + 懒加载

### 业务定位

资源详情是资源模块的“单一真相来源”：基础信息、开发状态、测试、签约结算、领域工具、语言水平、服务价格、简历/教育/工作/项目、操作记录等都在这里维护（`pages/resourceManagement/resourceDetail/_id.vue:17`）。

### UI/交互设计（面试重点）

1) **Tab 导航 + 卡片区**：顶部 tab 切换 + `ref` 定位每个卡片，解决“信息很多找不到”的问题（`pages/resourceManagement/resourceDetail/_id.vue:10`）。
2) **卡片拆分（单卡单职责）**：例如 `basic-info-card / development-info-card` 通过 props 注入数据与方法，降低主页面复杂度（`pages/resourceManagement/resourceDetail/_id.vue:21`、`pages/resourceManagement/resourceDetail/_id.vue:42`）。
3) **状态机与字段权限统一口径**：详情页通过 `getAvailableStatusOptions / isFieldEditable / isFieldDeletable` 驱动 UI（`pages/resourceManagement/resourceDetail/_id.vue:2944`、`pages/resourceManagement/resourceDetail/_id.vue:2987`；状态机/权限配置见 `config/resourceStatus.js:54`、`config/resourceFieldPermission.js:330`）。
4) **关键动作兜底（入库前校验）**：把状态切到“已入库(120)”前，强制校验必填项，避免“状态成功但资料不全”（`pages/resourceManagement/resourceDetail/_id.vue:3076`、`pages/resourceManagement/resourceDetail/_id.vue:3164`）。

### 文件上传/下载在资源详情的落地点

- 合同 PDF 上传/预览/下载：`pages/resourceManagement/resourceDetail/_id.vue:3771`、`pages/resourceManagement/resourceDetail/_id.vue:3822`
- 简历/作品集/BVC 上传下载复用模块：`utils/resource/useResumeFile.js:74`
- 完整说明见：`docs/面试问答/上传下载-文件预览-详解.md:1`

## 6. 订单管理列表：为什么要做“高级搜索 + 批量动作 + 导出”

### 业务定位

订单列表是“业务运营的工作台”：日常筛选订单、批量确认/取消关键日期节点、按条件导出报表。

### 关键实现点

1) **高级搜索可折叠**：默认收起，减少压迫感；需要时展开更多日期维度（`pages/orderManagement/orderList.vue:61`、`pages/orderManagement/orderList.vue:66`）。
2) **搜索参数归一**：把多选状态数组 join 成后端期望的字符串（`pages/orderManagement/orderList.vue:1243`～`pages/orderManagement/orderList.vue:1245`）。
3) **统一接口调用**：查询走 `searchSalesOrderListByCondition`（`config/path.js:174`、`pages/orderManagement/orderList.vue:1254`）。
4) **列表内联更新**：批量确认/取消日期后，前端按 id 更新当前列表行，避免全量刷新造成“用户焦点丢失”（`pages/orderManagement/orderList.vue:1275`）。

## 7. 订单详情页：卡片化拆分 + SSR asyncData 并发拉取

### 业务定位

订单详情把一个订单拆成多个业务域：

- 客户信息（基础信息/结算节点）
- 生产信息（翻译记录、指派译员、评价等）
- 收益信息（利润相关）
- 操作记录

### 关键实现点

1) **卡片组件化**：`CustomerInfoCard/ProductionInfoCard/ProfitInfoCard/OperationRecordCard`（`pages/orderManagement/orderDetail.vue:171`）。
2) **SSR asyncData 并发拉取**：进入详情时并行拿订单、客户、生产记录、操作记录、收益数据，降低首屏等待（`pages/orderManagement/orderDetail.vue:257`～`pages/orderManagement/orderDetail.vue:325`）。
3) **角色差异化展示**：销售角色不展示生产信息和操作记录，避免越权/误操作（`pages/orderManagement/orderDetail.vue:222`、`pages/orderManagement/orderDetail.vue:32`、`pages/orderManagement/orderDetail.vue:72`）。

## 8. 译员平台：把资源详情“抽出来给自己用”，同时控制风险

### 业务定位

译员平台是“自助维护资料”的入口，目标是：

- 降低运营/PM 往返沟通成本（资料由译员自己更新）
- 让译员看到自己的合同、薪资、简历预览

### 关键实现点（可以讲成亮点）

1) **目录侧栏 + 滚动定位 + 完成度进度条**：引导译员按模块补齐信息（`pages/translator/index.vue:3`、`pages/translator/index.vue:21`、`pages/translator/index.vue:616`）。
2) **复用资源卡片组件**：基础信息/接单时间/领域工具/语言水平/服务价格/简历等卡片复用（`pages/translator/index.vue:35`、`pages/translator/index.vue:46`、`pages/translator/index.vue:57`、`pages/translator/index.vue:67`、`pages/translator/index.vue:87`、`pages/translator/index.vue:104`）。
3) **PDF 预览的稳定性**：预览用 fetch blob + pdf.js 内嵌，失败时提供下载兜底（`pages/translator/resumePreview.vue:165`、`components/PdfPreviewModal.vue:165`）。
4) **译员端下载接口隔离**：译员合同下载走 `translatorDownloadFile`，和后台资源下载区分开（`config/path.js:192`、`pages/translator/contract.vue:393`）。

## 9. 面试官常追问（建议你按这个节奏答）

1) **“你负责的模块业务价值是什么？”**  
   资源模块提高供给侧质量与可用性；订单模块保证交付与结算节点可控；译员平台把资料维护前置到译员自助，减少内耗。

2) **“你做的最难的技术点是什么？”**  
   资源详情大表单拆卡 + 状态机/字段权限 + 入库校验闭环；列表性能与可读性；上传/下载/预览的鉴权兼容。

3) **“你怎么保证线上不出问题？”**  
   关注 publicPath/CDN 版本、cookie 鉴权、CI 上传/部署链路；对应 Runbook：`docs/面试问答/常见故障排查-Runbook.md:1`。

### 故障复盘卡片（与本文主题相关）

1) 现象：多模块协作节奏不一致。  
- 影响：核心流程可用性或数据一致性受影响。  
- 定位：通过日志、埋点、接口返回与代码链路回溯定位到根因。  
- 止血：快速回滚/降级并加兜底判断。  
- 长期修复：补充边界校验、自动化测试与发布前检查项。

2) 现象：改造后出现跨模块联动异常。  
- 影响：上下游模块结果不一致。  
- 定位：接口契约、状态同步或配置项存在偏差。  
- 止血：统一契约并临时加兼容转换。  
- 长期修复：把契约收敛为单一来源并补文档与门禁。

3) 现象：高峰期下性能或失败率波动。  
- 影响：用户体验下降，工单增加。  
- 定位：识别瓶颈点（请求并发、渲染、缓存或鉴权链路）。  
- 止血：限流/重试/懒加载或拆分重任务。  
- 长期修复：建立持续监控与阈值告警，按周复盘。
