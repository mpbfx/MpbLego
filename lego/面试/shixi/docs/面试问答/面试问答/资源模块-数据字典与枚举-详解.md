# 资源模块-数据字典与枚举-详解（big-customer，面向面试）

> 目标：把资源模块里“后端码值 ↔ 前端展示”、“状态/阶段/权限”、“语言/领域/服务/单位/币种”等枚举的来源与使用点讲清楚，并指出项目里“单一来源”与“重复来源”的风险点。

## 1. 一句话概括（面试开场）

资源模块的数据字典分两类：

1) **强业务字典（必须与后端一致）**：资源状态（数字码 ↔ 中文）、测试类型、币种码值等  
2) **弱业务字典（前端展示/交互辅助）**：Tab 配置、表格列、筛选选项、标签分类、国家/城市列表等

核心原则：**码值（code）用于存储与接口，文案（label）用于展示；尽量保证“单一来源”，避免同一枚举在多个地方重复维护**。

---

## 2. 资源状态字典：code ↔ label ↔ 状态机（最核心）

### A) 状态映射（后端数字 → 前端中文 / 反向映射）

来源：`config/resourceStatus.js:5`

```js
export const statusMap = { 0: '新开发', 20: '沟通中', /* ... */ 120: '已入库', '-30': '已解约' }
export const statusReverseMap = { '新开发': 0, '沟通中': 20, /* ... */ '已入库': 120, '已解约': -30 }
```

使用点（举例）：

- 开发池行内状态编辑：`pages/resourceManagement/interpreterAndSuppliers.vue:1791`
- ResourceDetail 保存开发信息/入库校验：`pages/resourceManagement/resourceDetail/_id.vue:3074`

### B) 状态机（只允许 nextStates 流转）

来源：`config/resourceStatus.js:54`

- `statusMachine['测试通过'].nextStates = ['签约中', '测试不通过']`
- `statusMachine['签约完成'].nextStates = ['已入库']`

调用：`getNextStates/isStatusEditable`（`config/resourceStatus.js:125`、`config/resourceStatus.js:131`）。

落地：列表页与详情页都用“当前状态 + nextStates”生成下拉选项，减少误操作。

---

## 3. 阶段（开发 vs 在场）与字段权限字典

字段权限按“阶段”而不是“单一状态”来配置：开发阶段更自由，在场阶段更保守（不可删、部分必填）。

### A) 阶段枚举

来源：`config/resourceFieldPermission.js:11`

- `DEVELOPMENT_STATUSES`: 新开发/沟通中/.../签约完成  
- `ONSITE_STATUSES`: 已入库/已解约

### B) 字段权限配置（editable / deletable / required）

来源：`config/resourceFieldPermission.js:61`

```js
export const fieldPermissions = {
  development: {
    status: { development: { editable: true }, onsite: { editable: true, deletable: false, required: true } },
  },
  contract: {
    signDate: { development: { required: false }, onsite: { required: true } }
  }
}
```

统一入口：`getFieldPermission`（`config/resourceFieldPermission.js:330`）。

落地点：ResourceDetail 用 `isFieldEditable/isFieldDeletable` 驱动禁用与删除按钮（`pages/resourceManagement/resourceDetail/_id.vue:2987`）。

注意（面试加分）：当前“入库必填校验”并不是动态读取 `required`，而是写死在页面的校验清单（见 `pages/resourceManagement/resourceDetail/_id.vue:3164`），存在“双来源”风险。

## 4. ResourceDetailConfig：资源详情页的 UI 字典（tabs / columns / 选项）

`config/resourceDetailConfig.js` 是资源详情相关 UI 枚举的大本营，包含：

### A) Tab 字典（决定页面结构）

来源：`config/resourceDetailConfig.js:6`

- `tabs`: basic/development/test/contract/orderTime/domainTools/languageLevel/servicePrice/resume/...

落地点：`pages/resourceManagement/resourceDetail/_id.vue:10` 使用 tabNav + ref 定位。

### B) 表格列字典（test / languageLevel / servicePrice 等）

来源：`config/resourceDetailConfig.js:32`（例如 `testColumns`、`servicePriceColumns` 等）。

价值：卡片组件只需要消费“列定义”，避免列字段散落在多个组件里。

### C) 资源相关的静态选项（领域/服务/单位/测试类型/原因等）

来源：`config/resourceDetailConfig.js:295`

- `domainList`：`['游戏','影视','其他']`
- `serviceTypeList`：翻译/MTPE/.../AI配音/TEP
- `unitList`：`['字','分钟','小时','天','份']`
- `testTypeList/testTypeMap/testTypeReverseMap`（`config/resourceDetailConfig.js:305`）
- `translatorGradeList`：`['S','A','B','C','黑']`（在场筛选会用到）

### D) 国家/城市/时区字典（第三方标准化来源）

来源：`config/resourceDetailConfig.js:221`

- `countryList/countryOptions/cityList/chineseCities/timezoneMap` 来自 `countryDataUtil`，减少手工维护。

## 5. 资源类型字典：translatorType 的 code ↔ label

资源类型是典型“后端数字码 + 前端中文展示”：

来源：`utils/resourceDetailTransform.js:131`

```js
export const RESOURCE_TYPE_MAP = { 0: '海外个人', 2: '国内个人', 8: '海外供应商', 10: '国内供应商' }
export const RESOURCE_TYPE_REVERSE_MAP = { '海外个人': 0, '国内个人': 2, '海外供应商': 8, '国内供应商': 10 }
```

落地点：

- ResourceDetail 读取后端 `translatorType` → 展示 `resourceType`：`pages/resourceManagement/resourceDetail/_id.vue:1707`
- 保存开发信息时反向映射：`pages/resourceManagement/resourceDetail/_id.vue:3102`

与筛选组件的关系：

- ResourceFilter/OnSiteFilter 都维护了相同的 `resourceTypeOptions`（`components/ResourceFilter/ResourceFilter.vue:218`、`components/ResourceFilter/OnSiteFilter.vue:186`），属于“重复来源”。

## 6. 语言字典：value/label 与 getLabelByValue

语言字典来源：`config/languageOption.js:126`

- `languageOptions`: `{ value: 'en-US', label: '英语(美国)' }` 的大数组
- `getLabelByValue(value)`：`config/languageOption.js:157`

落地点（举例）：

- 列表聚合展示语言对：开发池 `decorateListForDisplay` 用 `getLabelByValue`（`pages/resourceManagement/interpreterAndSuppliers.vue:592`）
- 生产信息里语言对过滤：`components/OrderDetail/Cards/ProductionInfoCard.vue:301` 引入 `languageOptions`

面试补充：目前 `getLabelByValue` 是 `filter()[0]`，复杂度 O(n)。如果要优化，可构建 `Map(value→label)` 缓存（尤其在列表聚合里高频调用）。

---

## 7. 币种/单位：两套来源的对齐关系

### A) 币种（码值）

`config/currencyOption.js` 用数字 value 表示币种：

- `人民币=0, 美元=1, ...`（`config/currencyOption.js:1`）

生产信息卡也使用该枚举：`components/OrderDetail/Cards/ProductionInfoCard.vue:336`。

### B) 币种（文本列表）

`config/resourceDetailConfig.js` 里还有 `currencyList`（文本数组，`config/resourceDetailConfig.js:351`），并写了“与 currencyOption.js 保持一致”的注释。

面试讲法：

- “码值枚举”和“文本枚举”并存容易漂移，理想状态是只保留一种权威来源（例如只保留 currencyOption，并派生 currencyList）。

---

## 8. 签约结算：账户类型字典的“跨端不一致”风险

资源详情里有 `accountTypeList`（简化版）：

- `config/resourceDetailConfig.js:332`：个人/对公 + 中国境内/非中国境内（不带“外币/人民币”后缀）

译员平台合同页维护了“带币种后缀”的更细文案：

- `pages/translator/contract.vue:187`：`个人中国境内银行账号（人民币个人）` / `个人非中国境内银行账号（外币个人）` 等

ResourceDetail 的表单逻辑主要按“简化版”做条件渲染与校验：

- `info.accountType === '个人中国境内银行账号'`（`pages/resourceManagement/resourceDetail/_id.vue:3615`）

面试讲法（加分）：

- 这是典型“前后端/不同端的字典文案不一致”问题，建议把 accountType 做成“稳定 code + 展示 label”，并在不同端做 label 适配，而不是用字符串相等判断。

---

## 9. 当前项目的“单一来源”与“重复来源”清单（面试官最爱问）

### 单一来源（相对健康）

- 资源状态映射 + 状态机：`config/resourceStatus.js:1`
- 资源类型 code↔label：`utils/resourceDetailTransform.js:131`
- 资源详情 UI 配置（tabs/columns/大部分选项）：`config/resourceDetailConfig.js:1`
- 语言 value↔label：`config/languageOption.js:126`

### 重复来源（容易漂移，建议后续治理）

- ResourceFilter 的 `resourceStatusOptions/resourceTypeOptions/channelOptions/serviceOptions`（`components/ResourceFilter/ResourceFilter.vue:204`）与 `config/resourceStatus.js` / `config/resourceDetailConfig.js` 重复
- OnSiteFilter 的 `translatorLevelOptions/orderTimeRangeOptions/testScoreOptions/resourceTypeOptions`（`components/ResourceFilter/OnSiteFilter.vue:181`）与 `config/resourceDetailConfig.js` 部分重复
- 币种同时存在 `currencyOption`（码值）与 `currencyList`（文本）两套来源：`config/currencyOption.js:1`、`config/resourceDetailConfig.js:350`

---

## 10. 面试官追问：你会怎么演进这个字典体系？

1) 把所有跨端核心字典（status/resourceType/accountType/currency/testType）统一为 **code + label** 结构，并由后端下发或至少集中在 `config/` 单一来源。
2) 把筛选组件里的硬编码 options 替换为从 `config/resourceDetailConfig.js` / `config/resourceStatus.js` 派生。
3) 给字典加“静态校验”（CI）：例如扫描页面使用到的 status 文案是否都能在 `statusReverseMap` 找到。
4) 性能优化：对 `getLabelByValue` 建 `Map` 缓存，减少列表聚合时 O(n²) 的隐患。
