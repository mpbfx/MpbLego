# 资源字段权限 + 状态机详解（big-customer，面向面试）

> 目标：把“资源状态流转（状态机）”和“不同阶段字段可编辑/可删除/必填（字段权限）”讲成一条闭环：**配置怎么设计 → 页面怎么落地 → 保存/入库怎么兜底校验 → 面试追问怎么答**。

## 1. 一句话概括（面试开场）

这个项目把“资源的生命周期”拆成两层配置：

- **状态机**：用 `statusMachine` 定义每个状态是否可编辑、能流转到哪些状态（`config/resourceStatus.js:54`），页面根据 `getNextStates` 生成下拉选项（`pages/resourceManagement/resourceDetail/_id.vue:2944`）。
- **字段权限**：按“开发阶段 vs 在场阶段”控制字段 `editable/deletable/required`（`config/resourceFieldPermission.js:11`、`config/resourceFieldPermission.js:61`），页面用 `isFieldEditable/isFieldDeletable` 统一驱动表单禁用/删除按钮（`pages/resourceManagement/resourceDetail/_id.vue:2987`、`pages/resourceManagement/resourceDetail/_id.vue:3017`）。

一句话价值：**规则集中配置 + 页面统一消费 + 关键动作（入库）前强校验**，避免“状态乱跳/字段乱改”。

## 3. 状态机：怎么保证“只能按规则流转”

### A) statusMap / statusReverseMap：前后端状态值对齐

来源：`config/resourceStatus.js:5`

```js
// 后端数字 -> 前端中文
export const statusMap = {
  0: '新开发',
  20: '沟通中',
  '-10': '不合作',
  40: '备选库',
  50: '测试中',
  '-20': '测试不通过',
  80: '测试通过',
  90: '签约中',
  110: '签约终止',
  100: '签约完成',
  120: '已入库',
  '-30': '已解约'
}

// 前端中文 -> 后端数字（用于保存）
export const statusReverseMap = {
  '新开发': 0,
  '沟通中': 20,
  // ...
  '已入库': 120,
  '已解约': -30
}
```

面试讲法：

- UI 展示用中文（更直观），保存给后端用数字（更稳定、可枚举）。
- 双向 map 让页面“加载时可读、保存时可写”，避免 UI 层到处散落 magic number。

### B) statusMachine：把“可编辑 + 可流转下一状态”写成配置

来源：`config/resourceStatus.js:54`

```js
export const statusMachine = {
  '新开发': { editable: true, nextStates: ['沟通中', '不合作', '备选库'] },
  '沟通中': { editable: true, nextStates: ['不合作', '备选库'] },
  // ...
  '签约完成': { editable: true, nextStates: ['已入库'] },
  '已入库': { editable: true, nextStates: ['已解约'] },
  '已解约': { editable: true, nextStates: [] }
}

export function isStatusEditable(status) {
  const config = statusMachine[status]
  return config ? config.editable : false
}

export function getNextStates(currentStatus) {
  const config = statusMachine[currentStatus]
  return config ? config.nextStates : []
}
```

面试高频追问：前端限制了流转，后端还需要限制吗？

- 需要。前端限制是“减少误操作”，但**安全与一致性必须由后端兜底**（比如校验当前状态是否允许变更到目标状态）。
- 本项目里前端主要用于“生成下拉选项 + 禁用状态编辑”，不会替代后端的业务校验。

### C) 页面怎么用状态机生成下拉选项

来源：`pages/resourceManagement/resourceDetail/_id.vue:2944`

```js
getAvailableStatusOptions(currentStatusText) {
  const options = []
  if (currentStatusText) options.push({ label: currentStatusText, value: currentStatusText })
  if (isStatusEditable(currentStatusText)) {
    getNextStates(currentStatusText).forEach(text => options.push({ label: text, value: text }))
  }
  return options
}
```

讲法要点：

- “当前状态”永远保留在下拉里（可保持不变）。
- 只有当 `editable` 才追加可流转的 `nextStates`。

## 4. 字段权限：怎么保证“不同阶段字段能改/不能删/必填”

### A) 阶段（stage）判定：开发阶段 vs 在场阶段

来源：`config/resourceFieldPermission.js:11`

```js
export const DEVELOPMENT_STATUSES = [
  '新开发', '沟通中', '不合作', '备选库',
  '测试中', '测试不通过', '测试通过',
  '签约中', '签约终止', '签约完成'
]

export const ONSITE_STATUSES = ['已入库', '已解约']

export function isDevelopmentStage(status) {
  return DEVELOPMENT_STATUSES.includes(status)
}
```

面试官可能追问：为什么不用“状态码”来判定阶段？

- 当前实现是用“中文状态文本”判定阶段（`isDevelopmentStage`），因为页面层大量用中文展示。
- 可改进：用 `statusCode`（数字）判定阶段更稳（避免中文文案变化导致误判），或者直接在后端返回 `stage` 字段。

### B) fieldPermissions：用“分类 + 字段名 + 阶段”描述权限

来源：`config/resourceFieldPermission.js:61`

```js
export const fieldPermissions = {
  basicInfo: {
    name: {
      development: { editable: false, deletable: false, required: true },
      onsite: { editable: false, deletable: false, required: true }
    },
    loginAccount: {
      development: { editable: true, deletable: false, required: false },
      onsite: { editable: true, deletable: false, required: false }
    }
  },
  development: {
    status: {
      development: { editable: true, deletable: true, required: true },
      onsite: { editable: true, deletable: false, required: true }
    }
  },
  evaluation: {
    translatorLevel: {
      development: { editable: true, deletable: true, required: false },
      onsite: { editable: true, deletable: false, required: true }
    }
  }
}
```

面试讲法（抓住“差异点”）：

- 在场阶段 `deletable` 经常变成 `false`：意味着“资源已入库后不允许删关键数据，只允许补全/修改”。
- `required` 体现“入库必须补齐”的字段（但注意：本项目入库校验目前是**写在页面里**，不是动态读取 `required` 配置，见第 5 节）。

### C) getFieldPermission：统一入口，页面只问“能不能”

来源：`config/resourceFieldPermission.js:330`

```js
export function getFieldPermission(category, fieldName, resourceStatus) {
  const categoryPermissions = fieldPermissions[category]
  if (!categoryPermissions) return { editable: true, deletable: true, required: false }

  const fieldPermission = categoryPermissions[fieldName]
  if (!fieldPermission) return { editable: true, deletable: true, required: false }

  const stage = isDevelopmentStage(resourceStatus) ? 'development' : 'onsite'
  return fieldPermission[stage] || { editable: true, deletable: true, required: false }
}
```

追问点：为什么默认返回“全开权限”？

- 好处：新字段/新分类没配时不至于直接把页面锁死。
- 风险：漏配会导致“越权可编辑/可删除”。更稳的做法是：生产环境 default 改成“更保守”（比如不可删），并在 CI 做配置完整性校验。

## 5. 资源详情页落地：权限 + 状态机如何影响 UI/保存

### A) 页面统一封装：getFieldPermission / isFieldEditable / isFieldDeletable

来源：`pages/resourceManagement/resourceDetail/_id.vue:2976`

```js
getFieldPermission(category, fieldName) {
  const resourceStatus = this.developmentInfo.status || '新开发'
  return getFieldPermission(category, fieldName, resourceStatus)
}

isFieldEditable(category, fieldName) {
  if (this.isNewResource && category === 'basicInfo' && fieldName === 'name') return true
  if (this.isNewResource && category === 'basicInfo' && fieldName === 'email') return true
  if (category === 'basicInfo' && fieldName === 'loginAccount') return !this.basicInfo.loginAccount
  if (category === 'development' && fieldName === 'manager') return !this.isDevelopmentInfoSaved
  return this.getFieldPermission(category, fieldName).editable
}

isFieldDeletable(category, fieldName) {
  return this.getFieldPermission(category, fieldName).deletable
}
```

面试讲法：

- “配置 + 少量特判”是常见落地方式：通用逻辑放配置，少数强业务规则（比如登录账号只能填一次）在页面做特判。
- `loginAccount/manager` 这种“一次性字段”的规则比“状态阶段”更强，所以覆盖配置结果。

### B) 入库前强校验：防止状态改成 120 但信息不完整

来源：`pages/resourceManagement/resourceDetail/_id.vue:3060`

```js
const newStatus = values.status || this.developmentInfoEditing.status
const newStatusCode = statusReverseMap[newStatus]

if (newStatusCode === 120) {
  const missing = await this.validateOnSiteRequired(this.resourceId)
  // 当前编辑态有资源经理，则从 missing 中移除（保存后数据库就有了）
  const currentManager = values.manager || this.developmentInfoEditing.manager || ''
  const filteredMissing = currentManager ? missing.filter(item => item !== '资源经理') : missing

  if (filteredMissing.length > 0) {
    const fields = filteredMissing.map(n => `【${n}】`).join(' ')
    this.$message.error(`入库信息不完整，请补充 ${fields} 字段信息后再操作入库`)
    return
  }
}
```

再指向“校验清单”来源：`pages/resourceManagement/resourceDetail/_id.vue:3164`（按“基础信息/测试/签约时间/领域/语言/服务价格/译员级别”逐项校验）。

面试追问：为什么不直接读 `fieldPermissions.required` 做校验？

- 现状：入库校验写死在 `validateOnSiteRequired`，规则清晰但和 `required` 配置存在“重复来源”风险。
- 改进方向（能加分）：把 `required` 作为唯一来源，在入库动作时根据当前 `stage` 动态扫描所有 required 字段，并且把“列表至少一条有效记录”的规则（测试/价格/语言等）抽成可配置策略。

## 6. 面试官常问的追问清单（建议背诵的答法）

### Q1：状态机和字段权限为什么要拆开？

- 状态机解决“**状态怎么走**”（可编辑、可流转）。
- 字段权限解决“**字段能不能改/删/必须填**”，且规则跟阶段更相关。
- 拆开后复用更强：列表页只关心状态机，详情页既关心状态机也关心字段权限。

### Q2：如果后端新增了状态，前端要改哪些地方？

- `config/resourceStatus.js`：补 `statusMap/statusReverseMap/statusMachine`。
- `config/resourceFieldPermission.js`：把新状态加入 `DEVELOPMENT_STATUSES/ONSITE_STATUSES`（否则 stage 可能误判）。
- 资源详情页：确认 `getAvailableStatusOptions` 是否需要新增流转路径；确认入库校验是否新增必填项。

### Q3：这个实现最容易出问题的点是什么？

- **stage 推断依赖中文状态文本**：文案改动会影响权限判定（建议改成用状态码或后端返回 stage）。
- **getFieldPermission 漏配默认全开**：漏配会导致权限过宽（建议 CI 校验 + 生产环境更保守默认）。
- **required 配置与入库校验重复来源**：容易“配置改了但校验没改/或反之”。

## 7. 可改进点（面试加分项）

- 把 `resourceFieldPermission` 从“状态文本驱动”升级为“状态码驱动”，避免中文变更导致逻辑漂移。
- 把 `validateOnSiteRequired` 改成“读取 required 配置 + 策略校验”（列表型数据可抽象成 `atLeastOneValidRecord` 规则）。
- 给 `fieldPermissions` 加静态检查：扫描页面用到的 category/fieldName，CI 里保证都有配置（避免默认全开造成越权）。
- 清理无用依赖：`config/resourceFieldPermission.js` 里导入了 `statusReverseMap` 但未使用（`config/resourceFieldPermission.js:9`）。
