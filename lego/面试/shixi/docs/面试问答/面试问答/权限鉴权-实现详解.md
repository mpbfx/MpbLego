# 权限/鉴权实现详解（big-customer，面向面试）

> 目标：按“认证（是否登录）+ 授权（是否有权限）+ SSR 同构细节”的视角，把本项目的鉴权链路讲清楚，并配上关键代码摘录与追问点。

## 1. 一句话概括（面试开场）

这个项目的鉴权分两层：

1) **认证（AuthN）**：在 `nuxtServerInit` 阶段通过后端接口拉用户信息，设置 `store.state.authUser`；请求过程中如果接口返回 `errorCode === 1003`，会跳转到统一登录页（`store/index.js:14`、`plugins/http.js:28`）。  
2) **授权（AuthZ）**：以 `roleType + permission label` 为核心，前端主要通过 `v-checkPermission` 指令“隐藏/移除”不该出现的按钮或区块（`plugins/checkPermission.js:9`、`config/permission.js:1`），并辅以页面级 middleware（`middleware/checkPermission.js:4`）。

## 2. 关键文件索引（面试官要“看代码”时直接指路）

## 3. 关键代码摘录（按“链路”讲）

### A) SSR 初始化：nuxtServerInit 拉用户信息并标记登录态

来源：`store/index.js:14`

```js
export const state = () => ({
  authUser: null
})

export const mutations = {
  SET_AUTH_USER(state, user) {
    state.authUser = user
  },
}

export const actions = {
  async nuxtServerInit(store, { app, req }) {
    // 译员平台根据 url + cookie 做特殊处理
    const cookieStr = req && req.headers && req.headers.cookie || ''
    const requestUrl = req && req.url || ''
    const isTranslatorPage = requestUrl.startsWith('/translator')

    if (isTranslatorPage && cookieStr.includes('logged_out=1')) {
      store.commit('SET_AUTH_USER', false)
      return
    }

    if (isTranslatorPage) {
      const validUserRes = await app.$http.get(path.isValidUser)
      if (validUserRes.errorCode === 200 && validUserRes.data) {
        store.commit('userinfo/UPDATE_USERINFO', { userName: username, roleName: role, isValid: valid })
        store.commit('SET_AUTH_USER', true)
      } else {
        store.commit('SET_AUTH_USER', false)
      }
    } else {
      const userinfoRes = await app.$http.get(path.getUserInfo)
      if (userinfoRes.errorCode === 200) {
        if (userinfoRes.data) store.commit('userinfo/UPDATE_USERINFO', userinfoRes.data)
        store.commit('SET_AUTH_USER', true)
      } else {
        store.commit('SET_AUTH_USER', false)
      }
    }
  }
}
```

面试讲法：

- `nuxtServerInit` 只在 **SSR 首次渲染**触发（服务器端执行），用于把“登录态/用户信息”灌到 Vuex，避免首屏闪烁。
- 这段逻辑有两个业务入口：`/translator`（译员平台）与“非 /translator”（大客户系统），分别走 `isValidUser`/`getUserInfo`（`store/index.js:31`、`store/index.js:46`）。

### B) 请求拦截：`errorCode === 1003` 跳转统一登录页（认证兜底）

来源：`plugins/http.js:5`

```js
instance.onResponse(response => {
  if (response.data.errorCode === 1003) {
    store.commit('SET_AUTH_USER', false)
    const isTranslatorPage = route.fullPath && route.fullPath.startsWith('/translator')
    if (!isTranslatorPage) {
      redirect(`${path.loginUrl}=${process.env.WEBSITE_HOST}${route.fullPath}`)
    }
  }
  return response.data
})

instance.setBaseURL(process.env.API_HOST)
process.server ? instance.setHeader(cookie) : ''
```

配套登录地址配置：

来源：`config/path.js:1`

```js
const path = {
  loginUrl: 'https://f.youdao.com/login.do?back_url',
  getUserInfo: '/sales/base/getUserInfo',
  isValidUser: '/sales/user/isValidUser',
}
```

面试讲法：

- `1003` 被当作“未登录/授权失败”的统一错误码（同类约定通常由后端提供）。
- 登录跳转把当前页面拼到 `back_url`，实现“登录后回跳”。
- 这是“认证兜底”：即使页面没有 middleware，接口一旦返回 1003 也会把用户导向登录。

### D) UI 级授权：`v-checkPermission` 指令直接“移除 DOM”

来源：`plugins/checkPermission.js:9`

```js
const checkIfVisible = (roleType, label) => {
  const visible = permissionTable[label] ? permissionTable[label].includes(roleType) : false
  return visible
}

const checkPermission = Vue.directive('checkPermission', (el, binding, vnode) => {
  const roleType = binding.value.roleType
  const label = binding.value.label

  if (!checkIfVisible(roleType, label)) {
    const comment = document.createComment(' ')
    Object.defineProperty(comment, 'setAttribute', { value: () => undefined })
    vnode.elm = comment
    vnode.text = ' '
    vnode.isComment = true
    vnode.tag = undefined
    if (vnode.componentInstance) vnode.componentInstance.$el = comment
    if (el.parentNode) el.parentNode.replaceChild(comment, el)
  }
})
```

页面中使用示例：

来源：`pages/index.vue:5`

```vue
<template v-checkPermission="{ roleType: $store.state.userinfo.roleType, label:'usermanagement-searchUser'}">
  <!-- 有权限才渲染的区块 -->
</template>

<a-button
  v-checkPermission="{ roleType: $store.state.userinfo.roleType, label:'usermanagement-newUser'}"
>
  新建客户
</a-button>
```

面试讲法：

- 前端授权的最直观实现：**用指令在渲染阶段把无权限的 UI 直接替换为注释节点**（不是简单 `display:none`）。
- 指令依赖 `document`，所以应只在 client 侧运行；本项目里该插件通过 Nuxt plugin（client mode）加载（见 `nuxt.config.js:75` 附近的配置）。
- 注意：UI 隐藏只能防“误操作”，不能当作真正安全边界，真正的权限必须由后端校验。

### E) 路由级授权（middleware）：按路径映射到 label，再决定是否放行

来源：`middleware/checkPermission.js:4`

```js
export default function ({ store, redirect, route }) {
  const roleType = store.state.userinfo?.roleType
  const path = route.path

  // 译员平台不做权限检查
  if (path.startsWith('/translator')) return

  const getLabel = (path) => {
    if (path === '/costSettlement/cost') return 'costSettlement-checkOrderInfo'
    if (path === '/workloadAccount/projectManager') return 'workloadAccount-projectManager'
    if (path === '/workloadAccount/salesManager') return 'workloadAccount-salesManager'
    return ''
  }

  const label = getLabel(path)
  if (!checkPermission(roleType, label)) {
    redirect('/')
  }
}
```

面试讲法：

- middleware 是“路由进入前的守卫”，适合做“页面级权限”控制。
- 该实现是“路径 -> label”的映射方式，优点是简单直观；缺点是 label 覆盖面有限（没映射到的路径会落到 `''`）。

## 4. 现状评估（面试时可主动指出的“坑点/债务”）

1) `config/permission.js` 的 `checkPermission` 目前 **无论传入什么都 `return true`**（`config/permission.js:49-52`），这会导致 middleware 形同虚设；实际权限更多依赖 `v-checkPermission` 指令在 UI 层隐藏。  
2) `nuxt.config.js` 的 plugins 配置里存在“同一个对象写两个 `src`”的写法（`nuxt.config.js:75-78`），JS 对象后者会覆盖前者，容易造成某个插件根本没生效（之前提到的 `errorCodeHandler` 就可能因此没加载）。  
3) `middleware/auth.js` 中真正的 redirect 逻辑目前被注释掉（`middleware/auth.js:4-11`），路由级“未登录跳转”主要靠 `plugins/http.js` 的 1003 兜底。  
4) `plugins/http.js` 里 `instance.setHeader(cookie)` 的用法可疑（通常需要 `setHeader('cookie', cookie)`）；如果 SSR 请求没带 cookie，会导致服务端判断未登录，进而频繁 1003（`plugins/http.js:58`）。  
5) 项目里同时存在 `plugins/axios.js`（注入 `$api`）与 `plugins/http.js`（注入 `$http`）两套封装，面试时可以解释为“历史遗留/迁移”，但工程上建议收敛到一套。

## 5. 面试题库（Q&A 速记）

### Q1：认证和授权的区别？你们分别怎么做？

- 认证（是否登录）：SSR 初始化 `nuxtServerInit` 拉用户信息并标记 `authUser`；接口返回 `1003` 时跳登录（`store/index.js:14`、`plugins/http.js:28`）。  
- 授权（有没有权限）：`permissionTable[label]` 决定某个 `roleType` 是否可见，主要通过 `v-checkPermission` 控制 UI（`config/permission.js:1`、`plugins/checkPermission.js:9`）。

### Q2：为什么用 directive 来控制权限，而不是每个地方写 `v-if`？

指令可以把“权限判断 + DOM 移除策略”封装成统一能力，页面只关心 `label`；同时比 `display:none` 更干净（但依然不是安全边界）。

### Q3：SSR 场景下鉴权最容易踩什么坑？

SSR 端请求如果没带上浏览器 cookie（或 session），会出现“服务端认为未登录、客户端认为已登录”的不一致；本项目通过 `plugins/http.js` 在 server 侧从 `req.headers.cookie` 取 cookie 并尝试 setHeader（`plugins/http.js:8-14`、`plugins/http.js:58`）。

### Q4：如果让你改进，你会怎么做？

- 修正 `config/permission.js` 的 `checkPermission` 返回值，让 middleware 真正生效。  
- 把“路径 -> label”的映射改为更系统的方式（例如在 `pages` 里声明 meta 权限、或用配置表集中维护）。  
- 收敛 `$api/$http` 请求封装，统一 1003/2005 等错误码处理与跳转策略。
